# 低速・シーク・ループ中のクリックずれ

## 再現と原因

利用者の報告に合わせ、実際のフロントエンドをElectronで起動し、4パートとクリックのPCMを出力直前のAudioWorkletで分けて観測した。検証ウィンドウは非表示、出力は観測後にすべてゼロにする。利用者のセッションやマイクを使わない。原因の再現時はBluetoothのV31 AUDIO、44,100Hz、AudioContext.outputLatencyは285msだった。途中でV31 AUDIOが切断されたため一部は内蔵スピーカー（48,000Hz、報告遅延33ms）で検証し、インストール後にV31 AUDIOへ再接続して共通時計を確認した。

旧処理ではクリックだけをOscillatorで作り、無音の元音源のcurrentTimeから発音時刻を予約していた。

1. HTMLMediaElementを別々に開始すると、4パートと無音の元音源が数十msずれる。シーク・範囲変更・ループ後も差が残る。音が出ていない元音源はクリックの基準時計として不適切だった。
2. 実際に鳴るパートのcurrentTimeを使っても、音程保持を伴う速度変更では加工後のアタックがその時計からずれる。0.70倍速では約19〜53ms、0.50倍速では約50〜81msが残った。通常速度、または音程保持なしではこの差はほぼ消えた。

AudioContextを一時停止してグループ再開する案も比較したが、改善しなかったため採用していない。Bluetoothの報告遅延を一律に差し引く案や、曲・区間・速度ごとの固定補正は使用しない。

## 修正

元音源・4パートのステレオ各2チャンネルとクリック1チャンネルを、一つの11チャンネル音源にまとめる。パートなしの場合は元音源とクリックの3チャンネル。音楽の左右は32bit floatのまま保持し、クリックは現在の拍列からその都度作る。全チャンネルを一つのメディアで再生するため、音程保持・速度変更・シークの処理も一つになる。出力時に各ステレオ音源とクリックを分け、従来の音量・ミュートを独立して適用する。音楽を全ミュートしてもクリックは使える。

パートごとにクリックを付ける途中案では、実曲のパート間に最大約24msの差が残ったため、それも最終版には採用していない。各パートの操作用オブジェクトは一つの音源のチャンネル音量を操作するだけで、別のデコーダーを起動しない。独立したOscillator予約と、別のパート時計を選ぶ処理は削除した。シーク中のクリックも同じ音源が止めるので、遅れて届く画面イベントでクリックだけを消さない。

BPM・裏拍設定を変更した場合は現在の拍列で作り直す。曲名・ID・特定時刻・既知の補正量は判定に使わない。生成音源はブラウザ内のBlobで、保存済みの曲・解析結果を書き換えない。曲の切替では準備をキャンセルしてURLを解放する。モバイルは元音源だけを先に準備し、パート操作までは追加音源を読み込まない。途中のリセットでも、古い準備から遅れて再生が復活しないようにする。波形描画には元音源のサンプルを再利用し、11チャンネル全体を描画のために再デコードしない。

## 低速時のクリック音の分裂

共通音源へまとめた最初の版は、55msのクリック音そのものをクリックチャンネルへ入れていた。時刻は一致する一方、音程保持付きの速度変換が短いクリック音にも適用されるため、0.45倍などではクリック音まで引き伸ばされ、複数の短い音に聞こえる状態になった。

クリックチャンネルは引き続き共通デコーダー内に置くが、出力する音ではなく時刻マーカーとして扱う。速度変換後のマーカーをAudioWorkletで検出し、その場で45msの単発音を生成する。一つのマーカーが速度変換で分裂しても、元の55msを速度に応じて伸ばした期間と20msの余裕を再検出禁止期間にする。クリックを別時計で予約する方式には戻していないため、シーク・ループ・Bluetooth出力を含めて音楽と同じ経路から発音時刻を得る。

## PCM測定

`npm run test:audio` で再実行できる。実際の画面操作を行い、音が入った測定用WAVのアタックとクリックを観測する。予約式を逆算しただけの検証ではない。MediaElementAudioSourceが1本だけであることも検査する。各パートは異なる周波数の音を使う。13操作条件×4パートの52比較について、各比較3点以上、出力前の差が10ms未満であることを要求する。操作境界で比較対象がない音は別の拍へ誤対応させないため、250ms以上離れた対応を統計から除いている。境界での音の欠落を全面的に否定する検査ではない。さらに各条件でクリックの出力包絡を直接測り、0.25〜1.25倍速、シーク、ループ、範囲変更のすべてで単発音が約45.3msに収まることを確認する。

旧処理の値は最初の同一波形の4パート測定。最終版では異なる周波数の4パートへ検査を広げている。

残る約2〜3msは、測定用のアタックとクリックの立ち上がり波形の違いを含む。今回の出力前測定では、周回に伴う差の増加は見られなかった。Bluetooth機器から空気中に出る音は録音していない。「あらゆる環境で二度とずれない」という保証にはしない。

「さよならベル」の実際の元音源・4パートも別の検証ウィンドウへ読み込み、最終方式で0.70倍速・76.2〜92.8秒を50秒間ループした。準備は約5.3秒、実行エラーなし。検証時のメモリはElectron Browser約604MiB・Renderer約350MiB、Rendererのピークは約1,455MiBだった。短い合成音源だけで長い曲の読み込みを確認済みとはしていない。この実曲チェックは読み込みと継続再生の検査であり、上の2〜3msという値を実曲の全拍の測定値に読み替えない。

## 回帰検査と診断ログ

Nodeテスト49件、Pythonテスト215件・2サブテスト、画面テスト34件が成功した。ステレオの全サンプル保持、クリックがチャンク境界をまたぐ場合、複数サンプルレート、キャンセルも検査した。画面のテストは、描画停止中や5周のループでも実際のクリック音が続くこと、パート失敗時の復帰・全ミュート・モバイルの遅延読み込みを確認する。

`playback.ndjson` には1秒ごとに `playback-clock` を保存する。再生速度、元音源と各パートの時刻、共通音源を基準にしていること、AudioContextと出力側の時計、出力待ち時間、ループ範囲、クリックの有効状態を含む。シーク完了と速度変更も記録する。これは機器から出た音の録音ではなく、操作・デコーダー・出力時計の記録である。

## このMacへの反映状況

途中版 `abf5ef7` は1.3.0のままこのMacへ反映して再生・診断ログを確認した。その後の実曲検査でパート間の差が判明したため、全パートを一つにまとめる追加修正を行った。

最終版 `9a5f28c` も1.3.0を維持してこのMacへ反映した。旧版を正常終了してから入れ替え、署名、同梱UIとソースの一致、公開用解析一覧2ファイルの置換前後のハッシュ不変、起動、バックエンドの正常応答を確認した。「さよならベル」を0.70倍速・ループ・クリック有効で実際に再生した診断ログは `reference: "shared"` を記録し、原曲と4パートの時刻は各記録で一致した。この確認時は既定出力が `V31 AUDIO`、出力待ち時間が285msのBluetooth接続だったため、Bluetooth経由でも全音声が同じ出力経路と時計を通っていることを確認できた。
