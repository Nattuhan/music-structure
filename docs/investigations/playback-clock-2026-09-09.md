# 低速・シーク・ループ中のクリックずれ

## 再現と原因

利用者の報告に合わせ、実際のフロントエンドをElectronで起動し、4パートとクリックのPCMを出力直前のAudioWorkletで分けて観測した。検証ウィンドウは非表示、出力は観測後にすべてゼロにする。利用者のセッションやマイクを使わない。既定出力はBluetoothのV31 AUDIO、44,100Hz、AudioContext.outputLatencyは285msだった。

旧処理ではクリックだけをOscillatorで作り、無音の元音源のcurrentTimeから発音時刻を予約していた。

1. HTMLMediaElementを別々に開始すると、4パートと無音の元音源が数十msずれる。シーク・範囲変更・ループ後も差が残る。音が出ていない元音源はクリックの基準時計として不適切だった。
2. 実際に鳴るパートのcurrentTimeを使っても、音程保持を伴う速度変更では加工後のアタックがその時計からずれる。0.70倍速では約19〜53ms、0.50倍速では約50〜81msが残った。通常速度、または音程保持なしではこの差はほぼ消えた。

AudioContextを一時停止してグループ再開する案も比較したが、改善しなかったため採用していない。Bluetoothの報告遅延を一律に差し引く案や、曲・区間・速度ごとの固定補正は使用しない。

## 修正

元音源と各パートに、拍列からその都度作ったクリックを第3チャンネルとして付ける。音楽の左右チャンネルは32bit floatのまま保持する。同じメディアのチャンネルは同じ音程保持・速度変更・シークを通るため、処理後も音楽とクリックの位置関係を保てる。出力時に左右の音楽とクリックを分け、従来の音量・ミュートを独立して適用する。音楽を全ミュートしてもクリックは使える。

実際に鳴っているパートからクリックを1本だけ出す。元音源への復帰時や全ミュート時は元音源側のクリックを使う。独立したOscillatorの予約処理は削除した。BPM・裏拍設定を変更した場合は現在の拍列で作り直す。曲名・ID・特定時刻・既知の補正量は判定に使わない。

生成した音源はブラウザ内のBlobで、保存済みの曲・解析結果を書き換えない。曲の切替では準備をキャンセルしてURLを解放する。モバイルは元音源だけを先に準備し、パート操作までは追加音源を読み込まない。準備中のリセットや曲切替から遅れて再生が復活しないよう世代を検査する。

## PCM測定

`npm run test:audio` で再実行できる。実際の画面操作を行い、音が入った測定用WAVのアタックとクリックを観測する。予約式を逆算しただけの検証ではない。各条件の音声比較は3点以上、出力前の差が10ms未満であることを要求する。操作境界で比較対象がない音は別の拍へ誤対応させないため、250ms以上離れた対応を統計から除いている。境界での音の欠落を全面的に否定する検査ではない。

| 条件 | 旧処理の差（代表的な最大値） | 修正後の最大絶対差 |
| --- | ---: | ---: |
| 通常速度・4パート | 87ms | 2.18ms |
| 0.70倍速へ変更 | 108ms | 2.20ms |
| 0.70倍速で後方へシーク | 127ms | 2.18ms |
| 0.70倍速で前方へシーク | 114ms | 2.18ms |
| 0.70倍速の区間ループ | 142ms | 2.18ms |
| 再生中に範囲を移動 | 135ms | 2.18ms |
| 再生中に範囲を伸縮 | 136ms | 2.20ms |
| 0.50倍速のループ | 171ms | 2.45ms |
| 0.75倍速のループ | 123ms | 2.18ms |
| 1.00倍速へ戻してループ | 93ms | 2.18ms |
| 0.25倍速のループ | 未測定 | 2.45ms |
| 1.25倍速のループ | 未測定 | 2.40ms |

残る約2msは、測定用のアタックとクリックの立ち上がり波形の違いを含む。今回の出力前測定では、周回に伴う差の増加は見られなかった。Bluetooth機器から空気中に出る音は録音していない。「あらゆる環境で二度とずれない」という保証にはしない。

「さよならベル」の実際の元音源・4パートも別の検証ウィンドウへ読み込み、0.70倍速で76.2〜92.8秒を80秒間ループした。準備は約2.4秒、実行エラーなし。検証時のメモリはElectron Browser約486MiB・Renderer約556MiB、ピークはそれぞれ約741MiB・965MiBだった。短い合成音源だけで長い曲の読み込みを確認済みとはしていない。この実曲チェックは読み込みと継続再生の検査であり、上の合成音源の2msという値を実曲の全拍の測定値に読み替えない。

## 回帰検査と診断ログ

Nodeテスト49件、Pythonテスト215件・2サブテスト、画面テスト34件が成功した。ステレオの全サンプル保持、クリックがチャンク境界をまたぐ場合、複数サンプルレート、キャンセルも検査した。画面のテストは、描画停止中や5周のループでも実際のクリック音が続くこと、パート失敗時の復帰・全ミュート・モバイルの遅延読み込みを確認する。

`playback.ndjson` には1秒ごとに `playback-clock` を保存する。再生速度、元音源と各パートの時刻、選択した基準、AudioContextと出力側の時計、出力待ち時間、ループ範囲、クリックの有効状態を含む。シーク完了と速度変更も記録する。これは機器から出た音の録音ではなく、操作・デコーダー・出力時計の記録である。
