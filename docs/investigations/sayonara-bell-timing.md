# 音源を根拠にしたクリック解析の修正（2026-09-09）

曲名・曲ID・固定時刻による分岐や補正ファイルは使用しない。最初に追加した曲専用レシピと、再解析でその固定値を引き継ぐ処理は削除した。

## 解析処理

`scripts/analyze_audio.py` はモデルの拍推定後に、元音源と拍列を `refine_timing_from_audio` に渡す。初回も再解析も同じ処理で、保存済みセッションや補正情報を参照しない。

- 冒頭は最初の32拍と小節頭が安定し、その前に同じ8分音符の位相を裏付けるアタックが複数ある場合だけ欠落拍を補う。無音や位相の合わない自由なイントロは補わない。
- 曲中は拍間隔が伸びた候補区間の前後3小節を比較する。前後のテンポが一致する場合も、それだけでは変更しない。
- 候補区間の音源から強いアタックを抽出し、前後のテンポに対応する8分音符上の位置を求める。すべての強いアタックの一致、複数の裏拍、複数の小節頭、区間両端の一致を要求する。アクセントの並びは固定しない。
- 根拠が揃った区間だけ、音源で確認した小節頭を結んで拍を復元する。単にテンポが違う区間や根拠のない区間は維持する。

判定は4/4の短い区間に限定する。実際のテンポ変更まで一律に平坦化しないため、根拠が不足するケースは変更しない。

## 検証

人工音源では複数のテンポ・開始位置・裏拍位置・別のアクセント列を試す。真のテンポ変更、無音、位相の合わないアタックを変更しないこと、逆相ステレオでも判定できること、補正の再適用で拍が増えないことを確認する。解析の入口から2回独立に処理しても、曲情報や保存済み補正なしで同じ結果になることも検証する。

CPUで元音源をモデルから再解析した最終検証でも、未補正出力は572拍・先頭1.83秒となり、問題区間の誤検知が再現した。共通処理の結果は580拍・先頭0.282秒となった。保存した未補正のモデル出力に最終版の共通処理を独立に再適用し、解析の入口から得た拍列・小節頭・補正記録と完全一致することを確認した。曲IDや保存済み補正は入力していない。

Pythonテスト215件と2件のサブテストが成功。手元の他10曲の読み取り専用チェックでは変更は発生しなかった。Mac・Windowsの解析ランタイム用ビルド設定にも新しいモジュールを追加し、組み込み検査の対象に含めた。R2へのデータ同期・UI同期は行っていない。

## 実機からの再報告と出力前の計測（2026-09-09）

更新後に利用者からクリックのずれが再報告された。画面で確認した条件は0.70倍速、約1:16〜1:32の区間ループ、4パート併用。既定の音声出力はBluetoothのV31 AUDIO、44,100Hzだった。操作ログのループ折り返し時に出る約16秒のstem-resync差は移動区間の差であり、周回で蓄積したずれの証拠ではない。

既存のplayback.ndjsonには操作・再生位置・速度・強制同期の差は残るが、クリックの実際のPCM開始位置、AudioContext時計、出力待ち時間、各パートの継続的な再生位置は残らない。既存ログから取得できる条件を利用者に聞き直さず、不足する計測を調査側で補う。

別の非表示Electronウィンドウで、既存のcreateMetronomeをそのまま使用し、既知の時刻に12個の短い音を持つ合成WAVとクリックのPCMをAudioWorkletの別チャンネルで観測した。観測後の出力はすべてゼロにし、利用者の再生へ検証音を加えていない。マイク録音も行っていない。同じ既定出力でAudioContext.outputLatencyは285ms、baseLatencyは約5.8msだった。
