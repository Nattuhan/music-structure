# 不具合修正の原則

## 曲専用の例外で不具合を回避しない

報告された曲は、不具合を再現するための入力であり、正解を埋め込む対象ではない。「この曲だけ直ればよい」という考え方で実装しない。原因を特定し、同じ条件で起きる不具合を共通処理で修正する。

曲ごとのハードコードは絶対に禁止する。次のような実装は、置き場所や名称にかかわらず禁止する。

- 曲名、曲ID、URL、ファイル名、音源の識別情報による特別扱い。
- 特定の曲の正解時刻、BPM、拍列、区間、補正量をプログラムへ埋め込むこと。
- 曲専用のJSON、設定、補正テーブル、移行スクリプトなどへ固定値を移して回避すること。
- 手で直した結果を再解析後に上書きし、自動解析の不具合が直ったことにすること。
- 曲名の分岐を消しただけで、その曲にしか合わない数値や特徴の組み合わせを条件にすること。

数値の閾値や音楽上の規則を使う場合は、対象曲から離れても説明できる根拠を持たせる。別のテンポ、開始位置、編成やリズムでも成立するかを検証する。判定に必要な時刻や拍位置は、その都度、入力音源と解析結果から求める。

## 原因を確認してから変更する

症状、再現条件、観測した事実、原因の仮説を区別する。報告された症状を、調査しやすい別の症状へ置き換えない。例えば「ループ再生中のずれ」を、根拠なく「利用者のシーク操作の問題」と扱わない。

原因が不明なら、再現と計測を進める。怪しく見える処理を闇雲に変更したり、推測を原因として断定したりしない。未再現・未確認の点はそのまま記録し、修正済みと報告しない。

保存済みデータの修復と、データを生成する処理の修正は別の作業である。保存結果を書き換えて症状が消えても、生成側の不具合を直したことにはならない。

## 修正の成立を検証する

解析の不具合では、補正済みデータや曲専用情報に頼らず、元音源から初回解析・再解析を行って正しい結果になることを確認する。再生の不具合では、報告された速度、ループ条件、音源構成などを再現し、実際の再生時刻や音声を確認する。

検証には、報告された事例に加えて、条件を変えた事例と変更してはいけない事例を含める。例えば、拍の誤検知を直す処理が本当のテンポ変化まで消していないかを確かめる。既存テストの成功や、実装と同じ計算を書いたテストだけで正しさを判断しない。

実在曲の観測値を調査記録や回帰テストの期待値に残すことはできる。ただし、それらを実行時の判定や補正の入力に使ってはならない。

## 記録と完了報告

変更理由、確認した原因、検証条件と結果、残る不確実性をコメントや調査記録に残す。コードの修正、保存済みデータへの適用、インストール済みアプリへの反映、公開・同期の実施状況を分けて報告する。未実施の段階まで完了したように伝えない。

これらを満たせない場合、曲専用の例外で完了扱いにせず、何が確認できておらず、何の検証が必要かを明記する。
